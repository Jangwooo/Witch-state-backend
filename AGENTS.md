# Repository Guidelines

## Project Structure & Module Organization
- `app/main.go` is the entrypoint for the Fiber API server.
- `internal/` holds application layers: delivery (HTTP), usecase, repository, and infrastructure/bootstrap.
- `ent/` contains generated Ent ORM code (do not edit manually; update schemas elsewhere and regenerate).
- `docs/` stores Swagger artifacts (`swagger.json`/`swagger.yaml`) generated by swag.
- `pkg/` holds shared utilities; `dto/` and `domain/` define data contracts and domain types.
- `docker-compose.*.yml`, `Dockerfile.*`, and `.env*` manage dev/prod runtime setup.

## Build, Test, and Development Commands
- `make dev-start` — build and run the dev stack via `docker-compose.dev.yml`.
- `make prod-start` — pull the latest image and run the prod compose stack locally.
- `make swagger` — regenerate Swagger docs from `app/main.go` annotations.
- `go run ./app -mode=dev` — run the API directly (requires local env/services).

## Coding Style & Naming Conventions
- Go formatting: use `gofmt` (tabs for indentation, standard Go layout).
- Packages use short, lowercase names (e.g., `usecase`, `repository`).
- Exported identifiers use `CamelCase`; unexported use `camelCase`.
- Keep generated files in `ent/` and `docs/` out of manual edits.

## Testing Guidelines
- No `_test.go` files are currently present. When adding tests, use Go’s standard tooling:
  - `go test ./...`
  - Name tests `TestXxx` in `*_test.go` files.
- Prefer tests alongside the package they cover (e.g., `internal/usecase/...`).

## Commit & Pull Request Guidelines
- Commit history uses short, descriptive messages without prefixes (e.g., “stage, music api”).
- Keep commits focused and scoped to one change set.
- PRs should include: a concise summary, linked issues (if any), and notes on API/DB changes.

## Configuration & Runtime Tips
- Environment files: `.env` (dev) and `.env.prod` (prod). Keep secrets out of Git.
- Docker is the default runtime path; ensure Redis/Postgres are reachable per compose files.
